# iCare Fitness CRM 3.1.2 — Cloudinary image storage

**Status: locally tested release candidate. Preview only; no live deployment or upload has been performed.**

## Scope and approved settings

Manual upload with separate, unchecked image-specific Cloudinary consent; Canvas WebP encoding at 82% quality and a 1,600-pixel maximum long edge; profile pictures, resource images and form-linked images. Existing encrypted local data, small JPEG avatars, Firebase workspace format, authentication, real-time synchronization, JSON backups, CSV/XLSX and Google reporting code are retained. The Google reporting Worker is not part of this repair.

## How the new workflow works

### Profile pictures

1. Open Contacts and edit a fictional contact. Choose a picture and tap **Done** to save the original small 256-pixel JPEG avatar locally.
2. The saved Contacts card now contains a separate **Upload cloud copy** control. Saving or replacing an avatar by itself never invokes Cloudinary.
3. Tap Upload cloud copy. Confirm the client explicitly agreed to Cloudinary storage by checking the initially unchecked consent box; select **Approve manual upload**. Consent is for private coaching storage, not marketing.
4. A recently selected original is held only in memory until the manual upload, another original is selected, or the vault locks/reloads. If available, it is compressed to WebP with up to 1,600 pixels on its longest edge, without enlargement. Otherwise, the saved 256-pixel avatar is used. To obtain a higher-resolution cloud copy, reselect the original, save, and upload before leaving/reloading. The embedded small avatar is retained for offline use.
5. The app records consent time, source hash, deterministic image asset ID, and exact compressed pending bytes in the encrypted local workspace. It synchronizes the pending record to Firestore before transferring to Cloudinary. The server verifies the authorized coach's ID token, reads the committed workspace with that same token, verifies the record/consent/bytes and dimensions, and only then signs an authenticated upload.
6. A successful response replaces the pending record with a small cloud reference. Firebase synchronization shares that reference across linked devices. The status indicates whether cloud transfer and reference synchronization completed. The existing local avatar remains unchanged.

### Notes and form attachments

Select the fictional client → Notes & resources → save an image attachment; or select Journey forms → attach and save an image. Use the **Upload cloud copy** control on the saved attachment card. The same consent workflow applies to both. Progress photographs also require the existing granted photo permission. Non-image attachments are unchanged and do not get Cloudinary upload controls. Animated images become still images. The original resource attachment remains in the workspace.

### Retrieval and removal

- In another authorized, unlocked device on the linked workspace, use **View cloud image** to fetch and display the authenticated image, or **Download cloud copy** to save it. The server returns verified bytes rather than a signed URL; the preview uses a temporary object URL that is revoked on close or lock. A downloaded file is not encrypted by the CRM.
- After a failed upload, **Retry approved upload** reuses the same recorded compressed bytes and deterministic asset ID; a lost response/existing asset is verified against the expected bytes. **Cancel pending / remove cloud copy** removes the potentially created cloud object after committed withdrawal. No background image transfers are performed.
- **Remove cloud copy** commits a withdrawal before remote deletion and keeps the original local image. Failed removal stays marked for retry. A previous avatar cloud copy is retained until a replacement succeeds; after success it is retired and inaccessible through the CRM's image viewer, and **Remove previous cloud copy** enables manual cleanup. If the new source produces exactly the same asset identifier, no duplicate pending record is created; keep or remove the existing copy explicitly.
- Tracked copies must be resolved before deleting their client/attachment record. Legacy attachment copies have explicit legacy view/download/remove controls when no reference is stored. Untracked historical assets and JSON restoration may still need manual review/cleanup.

## Status meanings

- **Saved locally**: local avatar or attachment exists; no Cloudinary success implied.
- **Consent recorded / pending**: an approved image is queued for manual retry; it may exist only in local storage, or have been synchronized to Firebase.
- **Preparing / synchronizing consent / uploading**: active operation. Do not close the tab mid-operation if avoidable.
- **Cloud image saved / reference synchronized**: API confirmation and reference sync completed.
- **Sync incomplete / error**: original image and pending/reference information are retained; retry or resolve the Firebase conflict.
- **Consent withdrawn / cleanup pending**: retrieval is blocked by the CRM API, and remote removal may need to be retried.

The Backups connector status remains a configuration check only; it does not prove that Cloudinary accepts your credentials.

## Limitations and rollback

- This is not live-tested or independently security-audited. Firebase token checks and Cloudinary API interactions were simulated locally; Chromium UI and Canvas encoding were tested with synthetic data and blocked network.
- The existing 6 MiB Firebase workspace limit remains. A pending compressed image temporarily occupies space in that workspace (including base64 overhead); the application rejects operations that would exceed the limit, before transmitting the image. Ordinary original attachments still count toward the limit. This is not a storage migration.
- Consent is a recorded coach attestation, not a client-signed consent system. The cloud workspace is not end-to-end encrypted; authorized services can access it. Existing legacy assets may lack a new consent timestamp. Legacy reads/removals are constrained to their record/identifier. This is not a guarantee of compliance or permanent deletion from provider backups or previously downloaded files.
- Firestore and Cloudinary cannot be committed atomically in one transaction. Deterministic IDs, verified recovery, pending references, withdrawal markers and manual cleanup mitigate failures, but concurrent cross-device upload/removal or an interrupted network request can still require reconciliation. Avoid overlapping image operations on different devices; live race testing remains required. Existing pre-upgrade tabs should be closed before enabling this release because old code does not enforce the new UI workflow.
- Server-side reads fetch the existing committed workspace to check consent. No admin credentials or new rules are used, but this adds latency/read usage and requires an online linked workspace with automatic synchronization enabled. The application does not perform offline Cloudinary uploads. Downloads/consent checks are online only.
- Authenticated delivery URLs remain server-side; no expiring-link system was added. A signed URL that was previously obtained elsewhere, or provider backups/caches, is not controlled by this patch. Never distribute it. The local vault protects local at-rest records after migration; it cannot prevent compromised browser code or device access when unlocked.
- If you must roll back before live image tests, revert the Preview commit as a unit to the working V3.1.1 source. Once V3.1.2 cloud records or pending uploads exist, first reconcile any pending and retired assets and secure a verified backup. Older UI versions do not manage the new metadata. Do not downgrade blindly or clear IndexedDB. No Production rollback is needed because Production was not touched.
