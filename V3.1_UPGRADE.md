# iCare Fitness CRM V3.1 — security and native Excel

**Release candidate. Local automated verification completed; secure-origin staging and independent security review remain required before production deployment.** No GitHub, Firebase, Cloudflare, Cloudinary or Google settings were changed by this build.

## 1. What changed

The previous `icare-crm-v1` IndexedDB workspace store held `state` and `sync-v2.8` as plaintext. V3.1 starts locked and does not load or render any client data until Firebase login, server-side authorized-coach verification, and local passphrase unlock succeed. `/api/session` reuses the existing server authorization helper and `CRM_COACH_UID`. The existing Firebase SDK session persistence still remembers a private device. Every reload requires the device vault passphrase; each unlock requires network access to verify the authorized coach. The already unlocked app can continue saving offline; previously committed changes stay queued.

On first unlock the entire validated legacy workspace and sync metadata are encrypted together in one IndexedDB record (`vault-v3.1`) using AES-256-GCM, a fresh random 96-bit IV per write, 128-bit random device salt, PBKDF2-HMAC-SHA256 at 600,000 iterations, non-extractable CryptoKey, and authenticated account/project/envelope metadata. The plaintext keys are deleted in the same IndexedDB transaction that stores ciphertext. The encryption passphrase is not stored or transmitted by the CRM. Use a strong unique passphrase of at least 12 characters; save it in your password manager privately. Each browser profile/origin has its own vault. A forgotten passphrase is unrecoverable; unsynced edits may be unrecoverable. Do not clear site data to recover unless you have verified backups.

Sign out removes the in-memory key and workspace, stops the Firestore listener, disables reads/writes, clears private UI, broadcasts a lock to same-origin tabs, and calls Firebase signOut. If Firebase sign-out fails, the local workspace stays locked and the app offers retry. Previously issued network writes may finish; signing out is not a global token revocation or sign-out of other devices. Wait for current operations to finish before using Sign out. Browser or operating system compromise, malicious extensions, XSS, memory inspection, backups/caches outside the application, and forensic remnants of legacy plaintext are not prevented. The browser cannot guarantee physical secure erasure. Firebase, Cloudinary and reporting still receive their existing authorized data; this is not end-to-end cloud encryption. The Google reporting process is untouched. Exports (including automatic pre-import JSON) remain unencrypted and require secure handling. No independent penetration test or compliance certification has been performed. A browser password manager might store a password/passphrase if configured to do so; this is outside the app's control.

XLSX import and export use genuine OOXML ZIP workbooks in-browser, without an additional CDN or sending spreadsheet contents to a conversion service. Export writes explicit string cells (including leading zeroes and formula-like text) and a `Clients` worksheet. CSV tools remain. Import supports standard ZIP/deflate .xlsx, inline/shared strings, worksheet choice, supported date formats, simple zero-padded numeric cells, preview, mapping, validation and explicit approval of duplicate updates. Maximum 5 MiB input, 24 MiB expanded ZIP, 256 entries, 100 columns and 2,000 data rows. Files with formulas, macros, external workbook links, error cells, encrypted/protected archives, unsupported structures or nonunique headers fail closed. Legacy .xls is not supported. Custom Excel formatting, arbitrary date formats, data already lost to Excel numerical rounding, and full Excel feature compatibility cannot be guaranteed. Use values-only worksheets with a single header row and ISO dates; export is contact/administrative data only, not a full workbook backup of clinical records or photos. Large exports may exceed the import limit. Use JSON for full workspace portability.

## 2. Required staging tests (before any production commit)

1. Extract ZIP to a new local folder; run `npm test` using Node 22 or newer, then `node build-pages.mjs`. No npm installation is required for the included tests. Verify 47/47. Read `REGRESSION_REPORT.md`.
2. Create a separate test environment using an isolated Firebase test project and test coach; do not change the existing production account, security rules or Cloudflare variables. If you cannot set up isolated test credentials, stop before live writes. For local test use the included loopback server with its `.env.example` copied to `.env` and filled with test project config and coach UID; do not commit `.env`. Cloudinary and Google credentials are not needed for the session endpoint. If the existing test rules need an authorized UID, set that only in the isolated test project. Launch `node --env-file-if-exists=.env server.mjs` from the extracted root; open `http://127.0.0.1:8787` in a fresh browser profile. Do not expose the development server publicly.
3. To verify migration: start a V3.0 copy on the same loopback origin first, add fictional contact, notes, photo, appointment, progress and training data; export JSON and confirm it opens. Close every V3.0 tab, stop that server, start V3.1 from its own folder on the same origin. Sign in to the test coach, choose a unique passphrase twice, and unlock. Compare the complete JSON export with the V3.0 backup excluding export timestamps. Verify DevTools Application → IndexedDB → `icare-crm-v1` → `workspace` contains `vault-v3.1` ciphertext and no `state` or `sync-v2.8` keys. Verify no key or passphrase is stored in the workspace. This does not guarantee forensic disk erasure.
4. Sign out and check the private UI disappears. Reload, test a wrong password, wrong coach, and wrong vault passphrase; verify no clients render and ciphertext remains unchanged. Sign in with the correct account and passphrase; check records. Repeat on a second tab and another device. Browser data belongs to origin: use the stable URL and don't confuse preview with production.
5. With fictional records only, test adding/editing/deleting from two devices, offline saving while unlocked, reconnecting, duplicate snapshots and concurrent edits. Confirm conflicts pause rather than overwrite. Verify sign-out locks other same-origin tabs, but not other devices. Check lock and unlock on Chrome/Edge, Safari/iOS and Android where used. Verify online unlock rejects a revoked/disabled test user. Do not assume revocation can be detected offline.
6. Test native XLSX import with two worksheets and a mixture of existing/new/invalid rows, use the mapping preview, skip or approve duplicates individually. Confirm no data changes before confirmation, notes/photos unchanged, existing blanks preserved, leading zeros retained. Test formula rejection and wrong file extensions. Export full directory, filtered directory and an individual client to both CSV and XLSX; open native XLSX in Microsoft Excel and compare values. Keep downloaded emergency JSON privately.
7. Existing cloud APIs: with isolated test resources, verify Cloudinary upload/download/delete, JSON backup/restore, Google Sheets reporting sync and privacy allowlist. If isolated credentials are unavailable, use mock regression results only and leave live verification pending. Google Sheets credentials, reporting-worker and binding are unchanged.
8. Have a qualified security reviewer assess the threat model and privacy requirements for actual client health information. Do not deploy this release to production before these acceptance tests pass and you approve.

## 4. Production migration and rollback precautions

Before approving deployment, export a full JSON backup from each device containing unsynced changes; verify file contents securely and check the cloud workspace is current. Close all older-version browser tabs on every device; older code can still write plaintext. Once V3.1 is deployed, use the stable production domain, sign in, create the passphrase twice on each browser, and verify the existing data. Do not erase IndexedDB, clear browsing data, or overwrite cloud data when the local vault is locked. If migration finds both encrypted and legacy records, it refuses to choose one. Preserve both and recover via the verified backup with technical support. Do not downgrade the encrypted browser store directly: V3.0 cannot read V3.1 ciphertext. If rollback is essential, export JSON while unlocked first, preserve the original encrypted vault, then restore via an isolated recovery browser/profile from a verified backup. Older code reintroduces plaintext storage. No changes are made to Firebase cloud schema; never manually modify cloud chunks.
