# iCare Fitness CRM V3.2.0 — Client Workspace Edition
## Preview-only installation, migration and acceptance guide

**Release candidate. Local development only. No GitHub commit, cloud deployment, live upload, real client data or credential changes were performed.** This version was built on the archived `iCare_CRM_V3.1.2_Complete_Cloudinary.zip`, not independently retrieved from the live repository. Compare your Preview branch against the V3.1.2 baseline before applying the patch. Do not overwrite unrelated changes.

### Approved scope
Hybrid design: persistent desktop module sidebar; mobile two-column module buttons and compact expandable profile details. All eleven client modules use the original client IDs and workspace collections. Existing storage and full available history reconstruction; new activity history bounded to the latest 300 recorded events per client, plus reconstructable existing records. No new database, external document storage or reporting feature changes. Manual Cloudinary upload and image-specific committed consent retained.

### Before changing anything
1. Keep a known-working V3.1.2 branch and deployment. In Cloudflare → Workers & Pages → your existing Pages project → Settings/Build, identify the exact Production branch. Confirm the chosen test branch is **not** Production. Do not push to the Production branch.
2. Export the full JSON backup from a currently accessible, unlocked V3.1.2 device and verify the file is present/readable. Include any unsynchronized changes. Keep this plaintext backup in encrypted, access-controlled storage. Do not send it to support or upload it to GitHub. Do not clear browser storage.
3. Back up the existing code (tag or download the exact Preview commit), and note your current Pages build command, output directory, Preview variable names, and service bindings without exposing values. Existing encrypted Cloudflare secrets remain untouched.
4. **Preview is not data isolation.** A Preview branch with the same Firebase project and coach UID can synchronize real data. For write, delete, consent and cloud upload testing, use a separately approved isolated Firebase project/coach, separate Cloudinary test environment and test reporting spreadsheet/Worker (or leave reporting disabled). Never attach the existing Production reporting Worker to a test deployment. Do not perform destructive tests against real clients.
5. Use a separate browser profile and stable Preview branch hostname to avoid mixing local vaults. A fresh deployment hostname may have different IndexedDB storage. Do not clear a previously used hostname. Do not reset existing passwords or passphrases.

### Exact GitHub file replacement
Use the separate patch archive; paths are repository-relative, not flattened. `PATCH_MANIFEST.txt` lists all changed and new files with SHA-256 digests. The core hosted application changes are `public/index.html` and `lib/cloud-consent.mjs`; the JSON schema, package test command and supporting tests/docs must be updated for a complete source release. The existing `lib/pages-cloudinary.mjs` helper and `functions/api/*` are unchanged. Do not replace your live root `wrangler.toml`, `.env`/secrets or `firestore.rules` from the full archive. Archived Firestore rules still contain an owner UID placeholder. Preserve the actual project name and existing configuration.

1. Extract the patch to a new local folder. In GitHub open the existing repository, select your Preview branch, then confirm the branch name. If needed create a new branch from the exact working V3.1.2 commit (this requires your separate deployment approval because a push may automatically deploy Preview).
2. Replace `public/index.html` with the supplied file. Replace `lib/cloud-consent.mjs` with its supplied counterpart. Preserve directory structure. Replace the root files indicated in the manifest, and add the new tests and release documentation. Do not upload any credentials, private backups or `.env` files.
3. Prefer a single atomic commit using GitHub Desktop or Git: clone the existing repo, check out the approved Preview branch, copy patch files into the matching folders, review the diff, then commit. Example commit: `V3.2.0 Client Workspace Edition (Preview only)`. Push only the approved Preview branch. GitHub web file uploads may create multiple commits/deployments; don't use them to deploy the application files separately. If using web UI, first prepare all files in a separate branch with deployment disabled until the complete change is ready.
4. Before pushing, run `npm test` using Node.js 22 or newer and `node build-pages.mjs` in the project root. Optional browser smoke test: Python + Playwright + Chromium, `python workspace-browser-smoke.py` (set CHROMIUM to your local binary path). The test intentionally mocks storage/auth and uses fictional records; it does not run the actual vault startup.

### Cloudflare Preview deployment — only after explicit approval
1. Open Cloudflare Dashboard → Workers & Pages → the existing Pages project (`icarecrm` in the previously supplied hostname; confirm actual name). Ensure Git integration uses the intended branch. Keep existing framework/build settings. The package expects build command `node build-pages.mjs`, output directory `public`, repository root, and API routes `/api/*`.
2. Verify Preview variables are present using the existing V3.1.2 settings. No new runtime variables or bindings are required. `FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, `FIREBASE_APP_ID`, `CRM_COACH_UID` are the required authentication settings; other Firebase config values remain optional. For Cloudinary image tests, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` must belong to the approved test environment. Never display keys/secrets or replace production values.
3. Preserve Preview-specific `REPORTING_SERVICE` binding if it is isolated; do not add a live production binding. The separate reporting Worker remains byte-for-byte unchanged. Its known `redirect:'error'` incompatibility remains a separate repair; do not enable it as part of this upgrade.
4. Push the complete approved Preview commit. Pages may automatically build/deploy it. Open Deployments and confirm the deployment is labeled **Preview**, the correct branch and exact commit. Do not merge to main. Never run `npx wrangler deploy` from the Pages root.
5. Use the stable Preview branch hostname where available. Authenticate with the isolated test account, unlock its vault, and run the acceptance tests below. Check `POST /api/session` returns 200 with authorized:true; don't copy authorization headers or tokens.

### Migration and preservation
Schema version stays 1. There is no eager rewrite or bulk conversion of existing data. Older V3.1.2 records are read without adding fields until a relevant edit is saved. Existing IDs, cloud metadata, source files, training data, account and revision metadata remain. Optional fields: client `endDate`, `activityHistory`; resource `noteId`, `url`, `photoKind`; progress `chest`, `hips`, `arm`, `thigh` in cm; training log `loggedAt`. Existing `formId` stays intact. The same resource record appears in the parent and Resources/gallery. New note/form attachments are committed with the parent in the existing encrypted transaction. Deleting a note/form explicitly unlinks but retains files in Resources. Resource deletion requires existing Cloudinary cleanup. No old avatars can be reconstructed if not retained; optional archive checkbox allows retaining the prior embedded avatar on replacement, with no transferred cloud consent.

### Rollback and recovery
Before any V3.2.0 writes, reverting the Preview branch commit should restore the previous code. After V3.2.0 writes, older V3.1.2 code can ignore new relationships/history, and deleting an old note in an older app may leave a new dangling association. **Do not simply downgrade a changed synchronized workspace or restore an old snapshot over newer data.** Pause use across devices, preserve a fresh V3.2.0 JSON backup and the original V3.1.2 backup, and compare IDs, attachment links, cloud references and revisions. Recover only in an isolated test workspace first. Retain both backups and the encrypted browser vault. If the old version must be restored, restore an explicitly reviewed compatible backup in a separate environment; never overwrite live data without explicit approval. Cloudinary assets may survive data rollback; reconcile them using the existing tracked cleanup workflow. No automatic password or vault reset. If an incorrect deployment hostname appears empty, revisit the original stable hostname rather than clearing storage.

### Limitations
The app remains a single-coach workspace, not a multi-user client portal. Firestore authorization is at the whole-workspace level; association checks are enforced by app validation and the Cloudinary backend, not per-record Firestore rules. The encrypted vault protects local at-rest data, not cloud end-to-end confidentiality or plaintext downloads. File type checks use extension and basic signatures; not antivirus/malware scanning. PDF sandbox rendering varies by browser. Office documents are downloaded, not rendered. Current photo archives are explicit; old overwritten history cannot be recreated. Activity history is bounded, application-managed, not immutable compliance logging. Existing 6 MiB serialized workspace limit remains and base64 increases file size. Preview/live authentication, real IndexedDB migration, cloud uploads, sync, Safari/mobile and independent security review require real isolated testing. Google reporting Worker compatibility fix remains pending.
